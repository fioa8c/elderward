Elderward

A single PHP file that finds what crept into a WordPress site, cuts out the malware it knows, and reads the access logs to show you how it got in.

$ curl -O https://raw.githubusercontent.com/fioa8c/elderward/main/elderward.php
$ php elderward.php scanall=1 scandirectory=/path/to/wp-root

Read the source on GitHub View elderward.php source

A first look at a compromised host

scanall=1 runs every scanner without changing anything and prints one list, worst first. The exit code tells cron and CI how bad it is.

investigator@host: /var/www/html 

      

    


    

      
Seven ways to look

      
Each scan mode is one flag. They run on their own, except scanall, which runs them all, and can pull in your logs too.


      

        

          
Signature cleanupphp elderward.php

          
Walks the tree and matches known injections, including the ndsw/ndsx and wqpq JavaScript campaigns, then removes them. Add dryrun=1 to see what would change first.

        

        

          
Everything, report-onlyscanall=1

          
Every scanner in one pass, sorted worst first. The signature pass is forced into dry run and restore=1 is ignored, so nothing on disk changes.

        

        

          
Integrityscanintegrity=1

          
Checks WordPress core, every plugin and every theme against the official wordpress.org package for the installed version. Reports modified, missing and extra files. Extra PHP inside core or a plugin is the classic dropped webshell. Works offline with checksumdir=.

        

        

          
Access logsscanlog=/var/log/apache2

          
Reads every access log in a directory, .gz included, for webshell requests, PHP served from uploads, wp-file-manager, Slider Revolution and TimThumb exploits, .env probes, traversal, and xmlrpc or wp-login floods. Add correlate=1 to find files modified within minutes of flagged traffic.

        

        

          
Quick checksquickscan=1

          
The cheap places attackers hide: executable PHP in wp-content/uploads, auto_prepend_file hooks in .user.ini and .htaccess, mu-plugins that load with no activation step, and hidden dotfile PHP.

        

        

          
Timestampsscantimes=1

          
Files changed after the rest of their package, and PHP whose modified time was pushed back with touch while the inode change time stayed put. These are leads, not proof.

        

        

          
Crontabscancron=1

          
The current user's crontab, checked for persistence: piped base64 decoders, pastebin downloads and droppers in tmp directories.

        

      

    


    

      
Wards it will not break

      
It runs on hosts that are already compromised, so it treats every filename, log line and API response as hostile.


      
    
        
  • 
          A dry run stays dry
          
    dryrun=1 covers every write, delete and restore. It reports what it would do and leaves the disk alone.
    
        
    • 
        
  • 
          Restores are verified first
          
    Each file from the official zip is checked byte for byte against the reference checksums before it's written. A tampered package is refused.
    
        
    • 
        
  • 
          Unknown files are never deleted
          
    Extra files are reported, and deleting them is your call. Set quarantinedir= to keep each original aside as evidence before it's overwritten.
    
        
    • 
        
  • 
          Writes can't truncate
          
    Cleaned files go to a temp file and are renamed into place, so a failed write leaves the original intact.
    
        
    • 
        
  • 
          TLS verification stays on
          
    An "all clean" answer must never come from an attacker sitting between the host and wordpress.org.
    
        
    • 
        
  • 
          Hunches never touch disk
          
    Timestamp and log-correlation findings are leads for you to follow. They never trigger a cleanup or a restore.
    
        
    • 
      

    


    

      
Output you can pipe

      
One line per finding, the same shape from every scanner, ready for grep, jq and tickets.


      

        

          
Text

          
The first three fields never contain commas. Paths and log content come from the compromised host, so control characters and commas in paths are percent-encoded. A crafted filename can't forge a finding line.

          
SEVERITY,TYPE,path,detail

        

        

          
JSON

          
format=json prints one event per line on stdout and moves progress to stderr, so stdout stays machine-readable.

          
{"event":"finding","severity":"HIGH",
 "type":"LOG_IOC","path":"...","detail":"..."}

        

      


      
What the exit code tells you

      
    
        
  1. 0
    Clean, or informational findings only.
    2. 
        
  2. 1
    Usage or fatal error. Check the arguments.
    3. 
        
  3. 2
    LOW, MEDIUM or ERROR findings to review.
    4. 
        
  4. 3
    HIGH findings. A successful cleanup exits 3 too: malware was found.
    5. 
      

    


    

      
Bring it to the host

      
No dependencies and no build step. Copy one file and run it.


      

        

          
    
            
  • PHP 5.6 or newer. The zlib extension is only needed for .gz logs, and zip only for theme checks and restores.
    • 
            
  • Shell access, or the ability to upload a PHP file and reach it over HTTP.
    • 
            
  • No shell? Set a long random WEB_ACCESS_TOKEN at the top of the file, pass it as ?token=, and delete the file when you're done.
    • 
          

          

            
Take a backup before cleaning. Preview with dryrun=1.

            
It finds known malware. A clean scan is not proof of a clean site, and log hits include plenty of attempts that failed.

          

        

        

          

            
$ php elderward.php dryrun=1 scandirectory=/path/to/site

            
          

          

            
$ php elderward.php scanlog=/var/log/apache2 correlate=1 scandirectory=/path/to/wp-root

            
          

          

            
$ php elderward.php scanintegrity=1 restore=1 quarantinedir=/safe/place scandirectory=/path/to/wp-root

            
          

          

            
$ php elderward.php help=1

            
          

        

      

    


    

      
Send what it missed

      
Elderward only knows malware someone has already caught. If you clean a site and find something it didn't flag, open a GitHub issue with a sample so the next scan catches it.


      

        

          
Put this in the issue

          
    
            
  • The file, zipped with the password infected so antivirus and GitHub don't strip it. GitHub won't take a bare .php attachment.
    • 
            
  • Its SHA-256 hash, and the path where you found it.
    • 
            
  • How it was loaded: an include in functions.php, an mu-plugin, a cron entry, auto_prepend_file, or something else.
    • 
            
  • The WordPress, plugin and theme versions, if you have them.
    • 
            
  • For attack traffic, the matching access log lines.
    • 
          

        

        

          
Package the sample

          

            
$ shasum -a 256 suspicious.php

            
          

          

            
$ zip -j -P infected sample.zip suspicious.php

            
          

          

            
Issues are public. Remove anything that identifies the site before you upload.

            
That means domain names, database credentials, salts, email addresses and visitor IPs in log lines. Never attach wp-config.php or a database dump.
